# 七日工作安排的有限实施约定

2026-11-17，承接用户无声收尾goal。根目录早期v0.3把完整排程列为P1，共同仓库后续统一总纲把进度重排列为核心闭环；此处记录差异，不把旧截止列表冒充排程。先完成纯规则候选与不变量检查，再接同一C确认/快照机制和页面，不另建影子任务库。纯规则通过不代表安排已持久化或T24—T27已完成。

输入为唯一仓库读出的任务/版本、用户明确提供的剩余分钟、带偏移的可用区间、既有工作块、当前时刻和不超过七天的范围。材料已准备不等于工作耗时为零；剩余工时由用户确认，不由模型猜。输入范围之外的既有块保留，跨范围边界、locked及done块不被重排。remainingMinutes表示当前尚需工作，已完成块不再次从中扣减；仍未完成的保留块会占用同一份剩余工作，避免重复排量。

仅对精确DDL生成能校验的截止前候选，date_only/unknown明确列出需补时刻，不补23:59。合并可用区间的并集，扣除不可移动块，按精确截止、用户优先级、稳定ID排序，按最多30分钟拆分到空闲区间。分钟网格向前起点取整、截止向下取整，不越过精确时刻；工时不足或截止前容量不足返回未安排分钟与原因。启发式未找到不代表全局无解，容量足够也不代表所有截止约束可满足。

不可移动块重叠、超出可用区间或不满足当前DDL/剩余工时等冲突保留原块并明确返回，阻止新安排掩盖问题。零工时不自动完成任务；新候选不修改任务DDL、工时或状态，不触发系统提醒。候选使用输入revision和任务版本形成稳定ID，重试可比较，不能随机创建重复块。

持久化计划将继续使用BusinessSnapshot.availabilityBlocks/planBlocks与原方案/回执的版本tag扩展，先记录协议与兼容，再接明确屏幕确认、全局revision和相关任务version复核；旧保留对象不得静默抛弃。当前本文为实施约定，未声称保存协议/页面/真实模型排程工具已接通。

首轮WeekPlanner纯规则已实现，14项主机检查/strictTS通过，含80组确定性工作量的无重叠/不超可用区间/不越DDL/不重复工时检查。未来范围外的保留块仍计入同一任务剩余工作，但不因未提供范围外空闲时间而制造冲突；已完成块不再扣剩余量。此处没有网络、OS或正式保存调用，尚未集成到SDK入口或手机。

## 接下来确认协议的实施约定（尚未实现）

计划使用`t16.proposal.v4`/`t16.operation.v4`和kind=plan_changes；复用原CommitEngine确认能力、幂等凭证、取消与单快照提交，不另建第二套确认引擎。v4只用于计划：不混入来源、材料或模型提交授权，普通任务操作继续写v2/v3。旧客户端对未知tag拒绝，旧v1/v2/v3保持读取。

PlanIntent四类：availability完整核对后的空闲区间；replan给出不超过七天的替换范围；lock明确锁定/解除某个未完成块；done明确完成某块并由用户同时提供该任务当前剩余分钟。done时剩余工时与块状态同一确认事务更新，不能根据块时长自行扣减工时；done为终态，不能重置已完成历史。模型可计算候选/提出草案，不能确认。

方案保存原availability/plan数组与涉及任务的真实旧快照/版本，after由可信C规则根据intent生成，不接收任意模型时间块。replan复算WeekPlanner，不能有未解决的不可移动块冲突；缺工时/精确时刻和容量缺口作为未安排项展示，可确认保存明确列出的部分候选。保留旧范围外、跨边界、done/locked块；不修改正式DDL。apply复核原数组与版本，方案、计划集合、工时变化和操作回执一致保存，冷重试返回原回执不再生成块。

旧保留集合中的未知对象不静默丢弃或猜成时间块；计划入口报不支持并保留，其余任务业务照常读。新v4出现后对已使用的计划集合增加结构/引用校验，不能因任务后续改期把旧计划当损坏删除；日期/工时变化造成的可执行性冲突由下一次预览明确报告。空闲设置可先于任务存在，故v4允许零任务changes/affectedTaskIds；done只允许同一任务remainingMinutes的明确变化。任务、材料和确认权限边界保持。

## 当前纯规则增量

已新增PlanningContracts/PlanningRules：完整明确的四类意图，空闲输入不接受外部ID，客户端派生稳定ID且保留时间瞬间未变的旧ID/写法；done需要明确剩余分钟，0合法、不自动扣计划时长、不改变任务状态或DDL；旧opaque集合拒绝解释并保留。14项排程加12项意图检查（含原80组工作量不变量）和strictTS通过。此处仅纯候选转换，v4编解码/CommitEngine/页面/真实存储仍未接入，没有向手机写v4。

v4待确认方案的operationId在可信暂存阶段预留并持久化，只是稳定幂等标识，不是保存成功或确认授权；只有实际回执证明提交。确认权仍只在屏幕动作后留于内存，重启须明确重新确认，沿用原预留operationId，不为同一安排重造标识。取消后也保留预留ID归属，不得被其他任务操作使用。旧v1/v2/v3的operationId语义不变。

v4固定当前意图与greedy-v1规范，后续算法修改须新增版本并保留v4验证路径，不能改变旧方案验证结果。apply按当前时钟复算候选的时刻和容量；发生变化则报过期，要求重新核对，不静默移动安排。已知待确认安排排他阻止新任务方案，生成安排前也要先处理其他已知待确认，避免无意使其失效；旧任务间的原有版本冲突语义不变。
