# 任务与材料确认的跨重启稳定编号

2026-11-17无声收尾复核。当前v4安排在暂存时显式预留编号；旧v1/v2/v3仍在confirm时向运行时申请随机编号，内存丢失且尚未提交时再次明确确认会得到不同编号，与项目的跨重启幂等约定不一致。新回归以真实C服务/合成文件复现：同一个pending方案，第一次operation-synthetic-7，fresh runtime后重新确认operation-synthetic-1。没有把此失败当通过。

有限修复保持既有记录字段和外部确认参数不变：对尚未提交的旧任务/材料方案，使用持久化proposalId及冻结命名空间派生128位SHA-256编号，前缀仍operation-；proposal在暂存后即稳定，因此不需要在confirm额外写一次业务快照或更改expectedRevision。此编号可预测，只作幂等标识，不是授权；重启后原请求仍必须CONFIRMATION_REQUIRED，屏幕重新确认后才可应用。v4保留原显式预留，旧applied始终重放其原存储回执与编号，不重算/迁移。

新的任务方案写入前检查派生编号与历史操作、其他方案预留/派生编号、内存确认请求冲突；确认时再次检查归属。取消后的proposalId和编号仍被预留，不供其他操作复用。冲突应保留数据失败，不能为同一方案悄悄换新编号。SHA函数及命名空间需保持兼容，不依赖时钟、随机数或本次运行时计数。旧客户端不具备此生成约定，不能据旧客户端复核结果宣称跨重启稳定。

回归覆盖普通v2任务与v3材料在全新运行时重新确认时编号不变、确认权未恢复、单回执；另核对旧v1/v2/v3回执重放、编号碰撞/归属及v4预留共存。SDK和手机验证需各自记录，不靠编号可预测性绕过屏幕确认。

旧主机测试有两处把“丢失授权”错误地绑定为“编号必须变化”，已改成编号稳定，同时保留重新确认前apply失败且原业务字节不变的检查。原随机operation运行时碰撞用例改为实际可能的遗留已存标识与新派生标识冲突、proposalId冲突，不移除碰撞保护。普通/材料两条先失败的新回归修正后通过；新增取消任务编号不得被v4预留再用，以及遗留pending可读但派生标识碰撞时拒绝夺取旧回执。失败日志保留在runtime，未称初次全通过。
