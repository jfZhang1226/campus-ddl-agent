## 1. 保存目标

让通知、任务、材料清单和会话在应用关闭后仍可读取。用户离线时可以回看本地内容，并按正式业务规则管理任务；新 AI 请求需要网络。

采用单用户、单设备本地数据模式。同一套业务代码通过 LocalStore 与必要的平台文件适配，分别使用鸿蒙和 Android 的应用私有数据目录；具体目录和 API 由 A、C 在实际工程中验证。代码仓库里的 fixtures 只是脱敏或人工样例，不是应用运行中的数据目录。

## 2. 拟定的文件组织

```text
应用私有数据目录/
├── task-store.json          # 正式业务快照
├── task-store.backup.json   # 上一份已确认有效的业务快照
├── task-store.tmp.json      # 写入过程中的临时快照
├── sessions/               # 每个会话独立保存消息与元数据
└── settings.json            # 时区、显示偏好等设置
```

task-store 的完整业务范围沿用总纲：通知、任务、清单、可用时间、计划、方案和操作记录放在同一个业务快照中。T03 只提供前三类字段和样例，后续任务补全其余实体。

下面是未来业务快照的空结构草案，不是两条样例文件的格式：

```json
{
  "schemaVersion": 1,
  "revision": 0,
  "notices": [],
  "tasks": [],
  "checklistItems": [],
  "availabilityBlocks": [],
  "planBlocks": [],
  "proposals": [],
  "operations": []
}
```

- `schemaVersion` 标识数据结构版本，用于升级与迁移，不在每次业务写入时递增。
- `revision` 标识整份业务快照版本，成功提交实际变化后递增，供方案检测全局变化。
- `Task.version` 标识单个任务版本，作用范围与全局 revision 不同。
- `fixtureFormatVersion` 仅标识样例包装格式，不代替 schemaVersion 或 revision。
- settings 和会话文件不保存服务商密钥；服务商密钥由 B 的服务端环境管理。

## 3. 启动读取思路

1. LocalStore 获取经过平台适配的应用私有目录。
2. 读取正式业务快照，检查 JSON、schemaVersion、字段、ID 引用及基础规则。
3. 正式文件有效时，加载到内存，由 Repository 提供查询。
4. 若正式文件缺失但存在备份或恢复痕迹，先进入恢复判断；不能把它当作全新安装而覆盖旧数据。
5. 若从未有业务数据且没有备份或恢复痕迹，初始化合法的空快照。
6. 正式文件损坏或不支持其 schemaVersion 时，保留原文件并提示；根据备份校验与恢复规则选择恢复路径，结构升级采用明确迁移过程。
7. 会话文件分别读取，单个会话损坏需有清楚提示，不因此删除正常业务数据。

临时文件不自动当成已提交业务数据，也不自动执行待确认方案。应用退出或确认后反馈中断的恢复，需要结合正式快照及后续操作记录判断。

## 4. 一次保存的思路

以下流程用于后续 T08/T16 实现与验证，不声称已经具有原子提交能力：

1. 页面或 Agent 产生修改请求；需要确认的操作先走方案与用户确认。
2. 所有业务写入进入串行队列，按最新已提交快照构造候选数据，避免同时写文件互相覆盖。
3. 校验字段、关联和业务规则；T16 中进一步校验版本及 operationId。
4. 将候选快照完整写入临时文件，完成必要的刷新与关闭，并校验可读取性。
5. 按已经验证的机制保留上一份有效快照为备份；备份失败时不假定保存成功。
6. 使用经过两端实测的文件替换机制将候选提升为正式快照。
7. 只有提交确认成功，才切换内存中的正式状态并向页面或 Agent 返回成功。
8. 失败时保留可重试输入或草案；页面不显示“已保存”，也不清除尚未完成的内容。

工具写入结果最终仍以实际提交结果为准。崩溃发生在替换之后但界面反馈之前时，T16 需要通过持久化的 operationId 返回已提交结果，避免重试重复创建。

## 5. 关闭、重启与恢复

| 情况 | 目标行为 | 后续验证任务 |
|---|---|---|
| 正常保存后退出并重启 | 从正式快照恢复同样的任务、来源与清单 | T08、T30 |
| 写临时文件失败 | 正式数据保持上一有效状态，提示失败并可重试 | T08、T30 |
| 写完临时文件、正式替换前退出 | 重启仍识别正式已提交状态，不自动提交临时草案 | T08、T30 |
| 正式快照损坏 | 保留损坏文件，检查备份并明确提示恢复选项 | T08、T30 |
| 备份损坏或结构版本不支持 | 保留现有文件并提示，不静默清空或覆盖 | T08、T30 |
| 确认后快速重复点击 | 同一 operationId 一次提交，返回已保存结果 | T16、T34 |
| 草案形成后用户又手工修改任务 | 版本冲突，重新读取并展示待确认差异 | T16、T34 |
| 会话保存失败但业务已经提交 | 分别呈现业务保存结果与会话失败，不能误称两者都成功；会话允许恢复或重试 | T11、T30 |

会话文件与业务快照是不同文件，单文件替换不等于跨文件事务。会话删除与未提交方案清理、恢复后的一致性检查，需要在 T11/T30 中一并验证。正式任务、来源关联、计划变化和操作记录则按总纲在同一业务快照中提交。

## 6. LocalStore 与 Repository 的分工

| 层次 | 负责什么 | 与谁对齐 |
|---|---|---|
| 平台文件适配 | 私有目录、读取写入、替换、备份和必要生命周期处理 | A 与 C，使用实际 ArkUI-X 工程验证 |
| LocalStore | 加载与校验快照、串行写入、备份恢复、结构版本 | C 负责，向上隐藏平台细节 |
| Repository | 查询与修改任务、来源、清单等业务对象，返回明确结果与错误 | C 与 A/B 对齐参数和返回值 |
| Agent/页面 | 生成草案、追问、展示差异与确认，按实际结果反馈 | B 与 A，D 核对交互状态 |

本次不承诺尚未验证的具体文件 API，也不把文件路径、任意 SQL 或原始写文件权限暴露给模型。
