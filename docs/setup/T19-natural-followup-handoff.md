## 当前差距

现在用户首次可以只贴原通知，由真实提取链路给出任务、日期和材料；后续答案仍通过卡片字段提交。`NoticeExtractionRequest` 与编码器只有原文、来源、发布时间、时区、上一轮draft和结构化answers，没有自由文本补充字段。不能只在页面加一个输入框，就声称网关已经理解自然语言答案；也不能把补充句拼进原通知、覆盖原文来源。

T17已有 `AgentLoop.run(message, context)` 和回答/澄清/方案结果，适合承接同一会话的下一条消息；但它不等于已实现跨输入上下文恢复。原017da8a的三项循环问题已在b189851修复，当前仍待schema/执行器入口校验收敛，D未接入该循环。原T19卡片也尚未统一到正式聊天owner。

## 建议的最小对齐

- A：确定正式聊天页/owner如何把原通知、当前草案和已有用户消息交给B，用户补充作为独立消息保存，原通知不改。切换会话、取消、编辑后过期响应要失效。
- B：先修新head当前schema/执行器评审问题，再明确通过既有对话入口解析补充消息的上下文契约及返回值。若决定在T12先增量支持自由文本，需同时定义长度限制、多轮累计、显式清空和向后兼容；由一条明确路线实施，避免两个入口对同一草案给出不同答案。
- C：继续保留受信客户端确认与T16一致提交；补充消息或模型返回不能获得确认/apply权限，不因模型说“已安排”就显示保存成功。
- D：在以上契约明确后，把补充输入/ASR转写送到同一会话，展示模型整理后的改动与依据，再复用现有卡片编辑、确认和真实回读。未发送输入不产生请求，未确认草案不写正式任务。

## 联调时应提交的实际结果

1. 首条仅粘贴缺日期通知，返回任务及必要追问；无需预填所有字段。
2. 下一条只说“截止是2026年11月24日”，仍保留原标题/材料/原文，截止只有日期，不补23:59。
3. 再说“改为25日下午六点”，须依据已知年份/月/时区或继续澄清，不能丢前两条消息，也不能影响另一个会话。
4. 用户改过标题或删过材料后，补日期不能把修改复原；取消或切换后，旧回复不能重新出现或覆盖新草案。
5. 模型完成整理后，正式任务数仍不变；只有屏幕确认才保存，并能失败重试、回读与重启核对。

以上五条尚未作为自然语言续轮实现或验收。当前已验证的是[卡片字段补日期路径](T19-date-validation-20261115.md)，当前小修只让字段提示即时刷新，不增加模型调用。
