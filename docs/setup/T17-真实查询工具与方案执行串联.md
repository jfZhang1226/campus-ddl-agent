## 2. 工具白名单与映射

模型只允许只读查询 + 保存草案；`apply_confirmed_proposal` 绝不在白名单内（由客户端确认事件触发，见 T16 `ClientConfirmation`）。

| 动作 | 输入 | 映射（T19 接入点） | 是否写入 |
|---|---|---|---|
| get_tasks | keyword/course/statuses/dateFrom/dateTo/includeUndated | `TaskRepository.list(TaskQuery)` | 否 |
| get_task_detail | taskId | `TaskRepository.get(taskId)` | 否 |
| get_notice | noticeId | 读取 Notice（当前 T14 无独立读取，见第 5 节） | 否 |
| get_availability | dateFrom/dateTo | T24 排程（当前占位 `NOT_IMPLEMENTED`） | 否 |
| propose_task_changes | sessionId/expectedRevision/notices/changes | `ProposalRepository.stage(ProposalDraft)` | 保存草案，不改正式任务 |

错误码契约与 T02/T14/T16 对齐：`NOT_FOUND / AMBIGUOUS_TARGET / INVALID_ARGUMENT / VERSION_CONFLICT / STORAGE_FAILED / CAPACITY_EXCEEDED / NOT_IMPLEMENTED / CONFIRMATION_REQUIRED / PROPOSAL_CANCELLED / ALREADY_APPLIED`。`AMBIGUOUS_TARGET` 由 agent 层在查询出多候选时产出（T20/T23），Repository 不猜测目标。

## 3. 循环与状态机（对齐 T02 第 3 节）

```
用户消息 → 模型 → tool_calls → 执行(查询/草案) → results 回传 → 继续
            │ answer/clarification → 结束
            └ propose 成功 → 交还客户端展示确认卡（循环结束）
```

- 每输入最多 `MAX_AGENT_STEPS=8` 步；连续两次相同（action+params+success）且无新增结果 → 终止并提示补充。
- 模型只负责生成草案；`propose_task_changes` 成功即返回 `proposal` 结果，等待客户端确认，不再继续循环。
- `propose` 失败（如 `VERSION_CONFLICT`）不当作方案，继续下一轮或由客户端展示失败。
- `apply`/`confirm`/`cancel` 不进入循环：由客户端在 `AgentOutcome.kind === 'proposal'` 时调 `ClientConfirmation`（T16），取消不写入、失败不报成功。

## 4. 接口

- `AgentTurn.turn(message, context, tools, results)`：注入的单轮网关调用，`results` 为累积工具结果。
- `ToolExecutor.execute(action, params)`：注入的工具执行器，返回归一化 `ToolResult {id,action,params,success,data,errorCode,message}`。
- `AgentLoop.run(message, context)`：返回 `AgentOutcome {kind: answer|clarification|proposal|error|limit, text, errorCode, proposalId}`。

T19 接入时，`ToolExecutor` 直接委托 T14/T16 的 repository，并把 `proposal` 结果交给确认卡；无需改动本循环内核。
