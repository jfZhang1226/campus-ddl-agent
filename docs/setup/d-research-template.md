# D：T05 通知收集与需求访谈模板

日期：2026-10-27。状态：模板已准备；真实通知 0 条，实际访谈 0 人。下面没有真实答复或已证实痛点。

## 1. 使用方式

先找 2～3 名同学，每次约 10 分钟，了解最近一次具体经历。由用户自行联系；本项目未代发邀请。说明用途并取得对方同意后再记录，默认只记匿名文字摘要，不录音、不要求导出整段聊天。

建议的开场白：

> 我们在做一个把课程通知整理成任务的小工具，想了解你平时怎么处理通知。可以聊聊你最近一次差点漏掉或处理起来比较麻烦的事情吗？我只记匿名要点，你不想回答的可以跳过。

这是沟通草稿，尚未发送。访谈不是让同学保证会使用，也不将“觉得不错”作为持续使用证据。

## 2. 每次访谈复制这一段

| 项目 | 实际填写 |
| --- | --- |
| 匿名编号 | 待填写，例如 R01；不记录姓名/学号/手机号 |
| 日期与方式 | 待填写 |
| 是否同意记录匿名摘要 | 待确认；未同意不记录个人内容 |
| 最近一次具体事项 | 待填写 |
| 通知从哪里来，后来是否有补充 | 待填写，来源用泛化标签 |
| 目前怎么记录、查看和提醒 | 待填写 |
| 最费时或最容易遗漏的一步 | 待填写 |
| 实际发生的后果/补救 | 待填写；没有发生则据实记录 |
| 对复制/主动分享/语音录入的接受情况与原因 | 待填写；不假设平台已支持分享 |
| 看两页原型时困惑在哪里 | 待填写 |
| 对方明确提出的需求 | 待填写，区分直接陈述与我们的解释 |
| 研究者解释、仍需追问的点 | 待填写，不能冒充对方原话 |

可按顺序询问：最近一次是什么事 → 收到后如何处理 → 后续变化怎么发现 → 哪一步麻烦 → 展示原型并观察能否找到确认/取消/原文。避免只问“你是不是经常忘 DDL”“你觉得我们产品好吗”等诱导问题。

## 3. 每条真实通知的记录模板

| 项目 | 实际填写 |
| --- | --- |
| 样例编号与序列编号 | 待填写；原通知和补充通知保持同一序列 |
| 来源类型 | 真实脱敏 / 合成；二者分别统计 |
| 是否获准在小组内用于开发 | 待确认 |
| 脱敏后的通知原文 | 待填写；移除姓名、学号、群号、私人联系方式、账号、敏感链接参数等 |
| 泛化来源标签 | 待填写，例如“某课程通知” |
| 通知发布时间 | 已知的可靠时间 / null；不拿导入时间冒充 |
| 导入/收集时间与时区 | 待填写 |
| 预期事项数量、课程、适用对象 | 待人工标注 |
| 日期精度与截止字段 | unknown / date_only / exact；未知保持 null |
| 提交渠道与材料 | 待人工标注；原文未写就保持未知 |
| 支持上述字段的原文片段 | 待填写 |
| 必须追问什么、禁止推断什么 | 待填写 |
| 开发集/留出集用途 | 待确定；已经用于开发的样例不再冒充留出样例 |

修改时间/课程等会影响语义时，要标注“已做情境改写”，保留对相对日期和通知先后的说明；不要将改写版当原始真实通知。真实数据先保存在约定的本地私有位置，脱敏和授权确认前不提交共同仓库。
