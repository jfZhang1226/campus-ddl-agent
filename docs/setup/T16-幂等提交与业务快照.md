# T16 幂等提交、确认与业务快照

C 主责；从 main@3a22a02 建立 feat/c-t16-confirmed-commit，已发布 PR #15，暂不合并。2026-11-12 根据 D 的交接缺口在原分支补创建型材料，并处理 B 的 ID 前缀意见；新增代码与验证状态见第11节。第7—10节保留原 v1 源码的阶段证据，不能用其空材料真机案例证明 v2 材料路径。本文给 A/B/D 接入与评审使用，正式页面和 Agent 串联不由诊断页替代。

## 1. 能力与边界

复用 T08 的 LocalStore、应用级 StorageCoordinator 和真实文件最后替换，复用 T14 日期/字段与来源校验。T16 新增持久方案、客户端确认和操作回执。一次正式提交在同一 task-store 快照中保存新通知、任务变化、新材料、方案 applied 状态和 operationId 回执；不分别调用多次 TaskRepository.create/update 或导入后补存材料。

当前支持一个方案中最多50项任务 create/update，可附带受信通知导入器准备的 Notice。来源 ID 必须真实存在或包含在本次待导入通知中；新通知均须被任务引用。模型不能直接指定新任务正式 ID、版本或审计字段。新任务 ID 在草案形成时由本地生成并预留，版本/审计时间在实际提交时产生。

v2 允许随本次 create 任务新建最多200项材料（方案总量）。每项材料的 ID 与 taskId 由客户端在 stage 中生成、绑定和预留，默认 state=pending、confirmedAt=null。update 不接受新增材料；已有任务的清单增删、勾选/准备、任务提交状态等继续由 T22 处理，不把它们伪装成新建操作。

删除及完整关联清理归 T30；计划变化的领域规则归 T25，完整状态转换/来源变化规则归 T22。当前不接受 delete/plan 操作，不静默跳过未知类型。availabilityBlocks、planBlocks 及其他未知 JSON 保持。T14 原先在 planBlocks/proposals/operations 非空时拒绝删除的保护不放开。

## 2. 应用级所有者与能力分离

使用 `getClientStorage(filesDir).commits`，它和 tasks/history 复用同一应用级 LocalStore/coordinator。不要在同一正式目录创建并行的存储所有者。测试可注入 FilePort 和 TaskRuntime。

| API | 用途 | 能否正式写任务 |
|---|---|---|
| `commits.proposals.stage(ProposalDraft)` | 保存待确认方案；只在业务快照加入 pending 方案 | 否 |
| `.proposals.get(id)` / `.list()` | 读取本版本支持的方案/差异；list只列T16记录 | 否 |
| `.confirmation.confirm(id, expectedRevision)` | **受信屏幕确认事件**产生内存授权，返回 `{proposalId, operationId, expectedRevision}` | 不写盘 |
| `.confirmation.apply(request)` | 检查持久回执或本次内存授权，单快照提交 | 是 |
| `.confirmation.receipt(operationId)` | 读取实际持久回执 | 否 |
| `.confirmation.cancel(id, currentRevision)` | 显式取消方案并撤销内存授权；不改变正式任务 | 否，方案状态会写盘 |

proposals 能力不含 confirm/apply。confirmation 是客户端受信能力，不是模型白名单工具，也不是鉴权服务；T17 必须由客户端真实确认事件触发，不能允许模型调用 confirm 或通过 `confirmed:true` 伪造。基础 LocalStore.save、TaskRepository 写方法仍不能直接注册为模型工具。C 未在本轮自行给 A/B 发送消息，本文是后续正式接口评审依据，不能声称 A/B 已同意。

## 3. 输入、输出及接入顺序

ProposalDraft 包含 sessionId、读取时的 expectedRevision、notices 和 changes。change 的 create 使用 taskId/expectedVersion=null；update 需要已有 taskId 与 expectedVersion；draft 为完整 TaskDraft，不是隐式补丁。update 的 before 由真实读取生成，页面可显示旧值和完整候选。

create 的 `checklistCreates` 是 `{label: string, sourceNoticeId: string | null}[]`。label 非空，非 null 来源必须属于**所在 change.draft.noticeIds**，并存在于已有或本次新通知；无来源的人工材料显式传 null。省略 checklistCreates 按空数组兼容旧调用方，显式 null 非法。不得输入材料 id/taskId/state/confirmedAt，也不接受 materials/checklistItems 等别名或未知修改字段；整个 stage 返回 INVALID_ARGUMENT，不保存部分方案。

stage 返回 `t16.proposal.v2`，顶层 `checklistItems` 含完整、顺序稳定的 ChecklistItem。A/D 应展示返回方案的任务、通知和材料，再从真实用户确认事件调用 confirmation；不能确认仅显示任务而遗漏材料的卡片。取消只留 cancelled 方案，不新增任何正式任务、通知、材料或回执。

Notice 是受信导入器准备的完整字段：ID、原文、来源、发布时间、导入时间、时区、contentHash。T16 校验字段和关联，不从模型的未经核验元数据生成来源事实，也不在此重新计算通知原文哈希或做相似通知去重；A/B 的导入器应按已有数据契约计算 SHA-256，T17 原始模型参数不可直接透传此内部参数。

接入顺序：

1. 从 TaskRepository 查询当前 revision/Task.version，准备并调用 stage。stage 读取后再次检查版本，存储层最终比较保存。
2. stage 返回完整 CommitProposal，展示变化并允许取消。**保存 pending 方案本身也使全局 revision 增加1**；返回的 proposal.expectedRevision 是保存方案后的 revision，确认时必须使用这个值，不能继续用 stage 的旧输入版本。
3. 用户看过当前方案后点击确认，客户端调用 confirm。重复点击同一未变化方案，返回相同 operationId；返回对象是副本，调用方修改不能改变内部授权。
4. 保留整个 request，再调用 apply。apply 只接受三个标识字段，不能附带新 changes 或确认标志。失败保留输入/request，不报“已保存”；明确重试复用原 request，不重新生成 operationId。
5. 成功时 data 为 CommitReceipt，含 operationId、proposalId、expectedRevision、committedRevision、resultStatus=committed、affectedTaskIds、changedTaskIds、提交时的 tasks 副本及确认/提交时间。v2 另有 notices（仅本次新建来源的完整副本）、createdChecklistItemIds、checklistItems（本次创建材料的完整副本，空集合也显式返回）。已有来源不重复新增，仍由 task.noticeIds/item.sourceNoticeId 引用。业务成功由这个真实结果决定，不能看聊天 status 或仅收到模型文本。
6. T16 内部统一返回 success/data/errorCode/message，operationId/committedRevision 位于成功 data。B 的 T17 工具适配如按总纲在顶层暴露这两字段，应从真实 data 映射；失败 committedRevision 不得伪造。A 应随后刷新当前任务查询，不能把历史回执中的旧 tasks 覆盖之后的新版本。

同值 update 不增加 Task.version/updatedAt，但新 operationId 与 applied 状态仍需一次正式快照提交，因此全局 revision 增加1；changedTaskIds 为空。如确认后只想查询结果，直接用 receipt。

B/T17 白名单参数须映射 checklistCreates，结果从真实回执映射 tasks/notices/createdChecklistItemIds/checklistItems，按 recordType 区分 v1/v2；不得对 v1 缺少的材料结果编造已提交。尚未支持的材料更新、删除、准备状态或未知字段应显式拒绝，不丢弃字段后声称保存成功。ID 都是不透明标识，不能按前缀解析业务类型；本次只修新生成 ID 的重复 task-，已有 ID 不迁移。

## 4. 幂等、冲突、重启与失败

- **先查回执，再查版本/授权。** 同一 operationId 与原 proposalId/expectedRevision 重试返回原回执，即使重启、当前全局 revision 已增加也不写盘。把 operationId 改绑另一个方案/版本，或附加新修改，返回 INVALID_ARGUMENT。
- 未提交的授权只留本次进程内存，绑定方案完整内容和版本。重启后 pending 草案仍在，但不能自动提交；旧 request 若尚无回执，必须重新显示并由用户明确确认。已提交方案可重新取得原 request/回执，不产生新操作。
- 全局 revision 变化使旧方案失效，包括别的方案形成/取消。返回 VERSION_CONFLICT 后重读真实任务，展示新差异、stage 新方案、再次确认。没有自动重基、自动改 expectedRevision 或失败重放；过期 pending 可用当前 revision 明确取消。
- 取消只保存方案 cancelled 状态，不创建任务/来源或操作回执。若取消与提交竞争，同版本的最后比较保存只允许一个生效。已经 applied 的方案不能取消来撤销业务，撤销需后续独立方案。
- 写入、flush、备份、最后替换失败，不返回伪造成功，已有正式主文件不提前改变，保留候选痕迹和原请求。若失败后重新读到该操作的正式回执，返回真实已提交结果，处理并发相同 apply 或替换成功但应答丢失；只读核对，不自动再次写盘。
- 如连回执核对也失败，返回“保存未获确认”，保留操作编号供读取或明确重试，不保证错误返回代表“绝未提交”。这一区别适用于不确定的底层替换应答。
- tmp-only、损坏/未知版本与备份恢复保持 T08/T30 语义，不自动提升、清空或重放草案。会话文件与业务快照仍不是跨文件事务；会话日志失败不能撤销或重复正式业务提交。

主要错误：INVALID_ARGUMENT、NOT_FOUND、VERSION_CONFLICT、CONFIRMATION_REQUIRED、PROPOSAL_CANCELLED、ALREADY_APPLIED，以及既有 STORAGE_FAILED/CORRUPT_DATA/UNSUPPORTED_SCHEMA/RECOVERY_REQUIRED。失败 data=null；操作未确认时不得显示已保存。

## 5. 存储兼容

业务 schemaVersion 仍为1，沿用已保留的 Object[] 集合。新 stage 使用 `t16.proposal.v2`，新方案提交产生 `t16.operation.v2`；包含材料字段（即使为空），材料 ID/所属任务/来源/默认状态及回执结果须与方案一致。同一材料 ID 不得被多个方案预留；pending/cancelled 的预留材料不能已在正式集合，applied 的材料必须存在并保持任务/来源绑定。回执是不可变创建结果，正式材料之后可变化状态，不反向修改旧回执。

继续读取原 `t16.proposal.v1` / `t16.operation.v1`，已提交操作原样重放，不迁移 ID/版本/回执；旧 pending 必须显式确认，仍生成原 v1 形状回执。v1 不能夹带 v2 材料字段。旧 v1 客户端遇到 v2 tag 返回 UNSUPPORTED_SCHEMA 并保留文件，不能降级 tag 让旧执行器忽略材料。未来未知 T16 tag 同样拒绝；其他未标识 JSON 保留，不自动执行或转成T16。

Proposal 持久化完整变更/旧值、新通知、来源、sessionId、expectedRevision、pending/cancelled/applied、createdAt 和 operationId。Receipt 与方案互相校验，且内容、创建/编辑版本和审计时间须匹配确认方案；回执保留提交时的内容，允许任务之后继续变化。全局正式回执版本上界由提交服务读取时检查；codec 也要支持“最后比较保存前 revision 尚未递增”的合法候选。
