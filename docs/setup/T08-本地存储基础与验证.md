## 2. 当前实现

| 模块 | 实现与边界 |
|---|---|
| `adapters/storage/FilePort.ts` | 私有目录文件接口：目录、存在检查、UTF-8 读取/刷新写入、同目录替换和列举 |
| `adapters/storage/ArkFilePort.ets` | 鸿蒙/Android 共用 `@ohos.file.fs`；从 context.filesDir 获取私有目录，不使用公共下载目录 |

| `data/LocalStore.ts` | 正式业务快照的存储基础；是内部接口，不能直接暴露给模型作为写入工具 |

| `data/storage/SnapshotCodecs.ts` | schemaVersion/revision、T03 字段类型/基础枚举/关联/日期字段组合、会话消息关联检查 |

## 3. 文件组织与真实提交点

```text
context.filesDir/campus-ddl/
├── task-store.json
├── task-store.backup.json
├── task-store.tmp.json
├── task-store.backup.tmp.json
├── task-store.recovery.tmp.json
├── task-store.corrupt-0.json       # 显式恢复前保留损坏主文件；不覆盖已有归档
└── sessions/
    ├── <sessionId>.json            # schemaVersion、revision、session、messages
    └── <sessionId>.backup.json     # 同样使用临时文件与备份机制
```

一次保存先冻结传入数据，排入队列后重新读取已提交快照并比较 expectedRevision。随后构造 revision+1 的候选，写临时文件、fsync、关闭、逐字读回并重新解析；将现有主文件写入备份临时文件并校验，再提升为备份；最后 rename 候选为主文件。

**主文件 rename 完成是本次存储提交点，之后不再安排可能把成功误报为失败的文件操作。** 不先 unlink 主文件、不在失败后清空数据、不让模型或页面凭文字认定成功。返回的数据从已准备的提交内容复制，调用者后续修改不会改变磁盘状态。

所有生产调用必须复用 `getClientStorage(context.filesDir)`。队列只解决当前应用进程、同一个 coordinator 内的并发，不提供跨进程/多个独立所有者的文件锁；不要在页面各自新建生产文件所有者。

文件内容 fsync 和同目录 rename 已接入，但目录元数据 fsync、突然断电耐久性与应用升级/重装行为还没有验证，不能称作已经具备数据库级事务保证。若两端真机显示方案不可靠，应先验证替代事务存储，再让正式业务依赖它。

## 4. 错误、恢复与未提交内容

| 情况 | 当前行为 |
|---|---|
| 首次使用且没有该记录的任何恢复痕迹 | LocalStore 返回合法空快照 revision=0；首次成功保存后落盘 |
| 会话从未保存 | NOT_FOUND，不伪造一条历史会话 |
| 正式文件缺失，但有备份、临时文件或归档 | RECOVERY_REQUIRED；不自动初始化或提升临时文件 |
| 正式文件 JSON/基础字段不合法 | CORRUPT_DATA，原文件保留；有有效备份时可以显式恢复 |
| schemaVersion 不支持 | UNSUPPORTED_SCHEMA，保留原文件；不通过旧备份静默降级 |
| 权限、读写、刷新或替换失败 | STORAGE_FAILED；不把权限错误当成文件不存在 |
| expectedRevision 过期 | VERSION_CONFLICT；重新读取与确认后再保存 |
| 候选数据或会话 ID 非法 | INVALID_ARGUMENT；不写文件，禁止路径穿越 |
| 单个会话损坏 | SessionIndex.issues 单独报告，其他会话和业务数据继续可读 |

recoverBackup 只在主文件缺失或损坏时恢复，先校验备份并保留损坏原字节，不允许将仍有效的主文件随意回滚。恢复会回到上一有效版本，调用方必须清楚提示用户；不会自动执行其中的待确认方案。

首次保存若在主文件形成前失败，可能只留下临时文件且没有备份。再次打开将要求恢复判断，不会猜测这些内容已经提交；当前不提供自动丢弃/提升这类痕迹的入口，人工修复与提示在后续恢复任务继续完善。已有主文件时的普通写入失败可以使用未变的 expectedRevision 重试。

T08 的 expectedRevision 只是存储层防覆盖保护。它没有实现 operationId 去重、客户端确认记录校验或完整 Proposal 事务；这些由 T16 对齐 B 后实现。页面和 Agent 不应提前绕过该层直接发布“已创建任务”。

## 5. A/B 接入方式

```ts
// 在应用所有者处获取，传给页面/Repository；不要让模型传 filesDir 或文件名。
const storage = getClientStorage(context.filesDir);
const result = await storage.local.read();
if (!result.success) {
  // 按 errorCode 提示恢复/重试，data 为 null，保留用户尚未提交的输入。
}
```

- LocalStore：read()、save(candidate, expectedRevision)、recoverBackup()。
- SessionStore：read(sessionId)、save(document, expectedRevision)、list()、recoverBackup(sessionId)。
- 返回结构：success、data、errorCode、message；成功时 data 为新快照，失败时 data=null。
- list() 的 data 为 sessions 和 issues；这是逐会话读取的列表，不是多文件一致事务快照。
- settings 尚未实现。会话删除、关联草案清理、业务与会话跨文件失败反馈在 T11/T30 接入，不假定本次已有。

### 本轮发现并修复的打包问题

通过 UIContext 动态获取 router 时，ACE 未收集到路由库；验证入口已改为显式 import。其后增量构建的 module_collection.json 只保留本轮变动的 router 项，导致先前新增的 file.fs 适配库未进入 APK。两种情况均是编译通过、真机调用失败，未被当作存储成功。

清理本工程生成缓存并完整重建后，module_collection.json 同时列出 ohos.router 与 ohos.file.fs，APK 包含 libfile_fs 等依赖，才得到上述通过结果。新增原生 API 或发现类似缺库时，在 client/ 执行：

```powershell
devecocli build clean
ace build apk --debug --target-platform arm64
& ../scripts/check-storage-apk.ps1
```

### 失败阶段与有效备份的区别

五项失败均由诊断 FilePort 将一次调用转向未创建的父目录或源文件，实际交给原 ArkFilePort 的文件 API 执行；不以单纯抛出模拟异常代替设备 I/O。返回必须为 success=false、data=null、STORAGE_FAILED，之后复用原 expectedRevision 重试。各场景使用不同人工目录，不操作生产 campus-ddl。

| 受控失败点 | 失败后主文件 | 失败后有效备份 | 重试 |
|---|---|---|---|
| 候选写入 | revision=2，原字节未变 | revision=1，原字节未变 | 保存为 revision=3 |
| 备份临时文件写入 | revision=2，原字节未变 | revision=1，原字节未变；候选临时文件保留 | 保存为 revision=3 |
| 备份提升 | revision=2，原字节未变 | revision=1，原字节未变；候选临时文件保留 | 保存为 revision=3 |
| 最后一步主文件替换 | revision=2，原字节未变 | 已提升为 revision=2，等于失败前主文件；候选临时文件保留 | 保存为 revision=3 |
| 恢复文件替换 | 人工损坏原文未变 | revision=1 未变；损坏归档与恢复临时文件保留 | 显式恢复 revision=1，原损坏归档仍在 |
