## 1. 项目定位与目标

### 1.1 一句话定位

面向大学生日常课程作业、实验报告、报名等通知，将分散的通知转成可执行任务，并在通知变更或进度变化时持续更新任务与安排的跨端 AI Agent 应用。

### 1.2 真实痛点

| 痛点 | 典型经历 | 本项目解决方式 |
|---|---|---|
| 通知分散、任务录入麻烦 | 课程群、班级群陆续发布通知，需要手动整理 | 粘贴通知或语音描述，提取任务，补齐必要信息后保存 |
| 截止时间和提交要求遗漏 | 记住要交报告，忘记还需要源代码、截图 | 同时提取 DDL、提交渠道、提交物，生成检查清单 |
| 补充通知难以关联 | 老师延期或新增附件要求，原待办没有更新 | 查询已有任务，展示变更，确认后更新原任务 |
| 多项任务集中到期 | 报告、作业、报名挤在同几天 | 结合剩余工作和可用时间，检查容量并生成安排 |
| 计划与实际进度脱节 | 今天没完成，后续安排也需要调整 | 用户反馈进度，Agent 查询相关任务并提出调整 |
| 写完与交完混淆 | 文件准备好了，却没有实际提交 | 将材料准备状态和用户确认的提交状态分开记录 |

上述痛点是待验证的需求假设。需求调研从向 2～3 名同学简单了解具体经历、收集 3～5 条脱敏通知开始；根据需要将交流对象扩展至累计 6～10 名，逐步验证最常出现、最影响使用的功能。

### 1.3 项目目标

1. 同一套 ArkUI-X 业务和 UI 代码，构建鸿蒙与 Android 两端应用。
2. 两端完成真实云端模型文本调用、会话本地保存与回看。
3. 鸿蒙完成 ASR → 模型/Agent → TTS 的语音交互。
4. 做通三个核心业务闭环：通知转任务、补充通知更新任务、进度变化后重排。
5. 通过可查看的任务变化和执行结果证明 Agent 确实操作数据。
6. 完成基本统一的视觉、状态反馈、异常提示和可复现的演示材料。

## 3. 功能范围与优先级

### 3.1 优先级定义

- P0：首版必须完成，包含命题硬性要求和核心业务闭环。
- P1：P0 稳定后完善，主要提升交互和使用体验。
- P2：选做，不纳入首版承诺。

### 3.2 功能清单

| 功能 | 优先级 | 首版范围 |
|---|---|---|
| 通知输入 | P0 | 用户主动粘贴文本；鸿蒙语音描述；录入通知发布时间 |
| 通知结构化 | P0 | 提取标题、课程/事项、截止时间、提交物、提交渠道，保留来源 |
| 多轮信息补齐 | P0 | 日期不明确、任务对象不明确时追问；允许先保存待补充任务 |
| 任务管理 | P0 | 新建、查询、编辑、删除、状态更新；支持人工操作 |
| 补充通知处理 | P0 | 查询候选原任务，展示前后差异，确认后更新，保留变更来源 |
| 提交清单 | P0 | 用户勾选材料准备情况，单独确认已提交 |
| 基础排程与重排 | P0 | 手动填写可用时间和剩余工时；安排未来七天；提示排不下的任务 |
| 两端文本与云端模型 | P0 | 一个模型服务商、非流式完整响应即可 |
| 鸿蒙语音 | P0 | 录音、ASR、文字核对、Agent 处理、TTS 播报与停止 |
| 会话本地历史 | P0 | 自动保存、重启恢复、回看、删除 |
| 数据和异常反馈 | P0 | 加载、超时、权限拒绝、保存失败、取消操作的明确状态 |
| UI 和交互完善 | P1 | 周视图、状态筛选、轻量动效、空态、语音状态反馈 |
| 系统到期提醒 | P1 | 根据实际 SDK/设备验证平台适配；拒绝通知权限不影响主流程 |
| 计划中断恢复 | P1 | 恢复待确认方案；恢复后重新检查数据版本 |
| 流式输出、Android 语音 | P2 | 基线通过后选择一项 |
| 截图 OCR、RAG、多模型、iOS | P2 | 有明确使用需求且剩余时间允许时再做 |

### 3.3 首版边界

首版采用单用户、单设备本地数据模式。跨端交付指同一套代码能在两个操作系统运行，不承诺两台设备自动同步；验收可在两端分别导入同一组示例。

通知由用户主动输入。自动读取微信/QQ 群聊、登录学习通或教务系统、自动上传作业、多人协作、跨设备同步均不在首版范围。提交状态由用户确认，不声称已向学校平台提交成功。

RAG 不作为首版必要依赖。当前核心信息来自通知原文和结构化任务库，任务查询可直接使用数据库/本地存储。若后续积累大量课程规定与提交规范，再评估带出处的资料检索；不为添加技术名词而引入知识库。

## 4. Agent 的作用与完整流程

### 4.1 与一次性模型规划的区别

首次规划的文字输出可能与直接询问大模型相似。本项目的价值来自持续使用中的信息关联与实际操作：

| 用户请求 | Agent 获取的已有信息 | 执行动作 | 可见结果 |
|---|---|---|---|
| “把这条通知记下来” | 通知发布时间、已有同类任务 | 追问缺项、生成创建方案、确认后保存 | 任务列表新增真实记录 |
| “老师说报告延期了” | 原任务、原 DDL、提交要求 | 匹配任务、生成变更、确认后更新 | 原任务变化，新增来源记录 |
| “今晚没做完，重新安排” | 当前进度、其他待办、空闲时间 | 补齐剩余工时、检查容量、生成新安排 | 保存新计划，标明未能安排的任务 |
| “报告写好了” | 提交清单、任务状态 | 询问材料与提交情况，更新对应状态 | “准备好”和“已提交”分别记录 |

大模型负责意图理解、信息提取、追问与工具选择；本地工具负责真实查询和写入；规则代码负责日期约束、数据校验和排程可行性检查。最终成功反馈以工具执行结果为准。

### 4.2 工作流一：通知转任务

1. 用户粘贴通知，填写或确认通知发布时间。
2. 通知原文先保存到本地，生成 noticeId。
3. 模型提取任务字段，输出待确认结构，不直接写入正式任务。
4. 对影响执行的缺项进行追问，如日期、课程、任务对象；提交格式未知可保留“待补充”。
5. 查询已有任务，检查可能重复的任务。
6. 展示任务卡：提取结果、来源、待补充项均可编辑。
7. 用户确认后，客户端工具校验并一次性写入。
8. 查询或读取提交结果，返回实际保存的任务摘要。

### 4.3 工作流二：补充通知更新任务

1. 保存补充通知。
2. Agent 根据课程、标题、任务时间查询候选任务。
3. 多个候选不能明确区分时，展示选择卡并追问。
4. 读取选定任务详情，生成字段变化：旧值、新值、依据原文。
5. 用户确认后更新原任务，保留原通知并追加补充通知关联。
6. DDL 或剩余工作变化可能影响计划时，提示是否查看调整方案。
7. 不因为截止时间变化而直接改写其他任务的正式 DDL。

### 4.4 工作流三：进度变化后的重排

1. 用户描述变化，例如“今晚没做完”“周末要参加活动”。
2. 查询受影响任务、已有计划和未来七天可用时间。
3. 追问缺少的剩余工时、可用时间或任务对象。
4. 调用排程工具生成候选安排，并返回无法容纳的任务。
5. 展示调整前后差异和简短理由，允许用户修改。
6. 确认后保存新安排；保留已完成时间块，替换选定范围内未完成的安排。
7. 用户下次反馈进度时，从已保存状态继续推进。

### 4.5 Agent 状态机

~~~mermaid
stateDiagram-v2
    [*] --> Idle
    Idle --> Understanding: 收到文本或语音转写
    Understanding --> Querying: 需要已有任务信息
    Querying --> Understanding: 返回工具结果
    Understanding --> Clarifying: 缺少必要信息
    Clarifying --> Understanding: 用户补充
    Understanding --> AwaitingConfirmation: 生成创建或修改方案
    AwaitingConfirmation --> Executing: 用户确认且校验通过
    AwaitingConfirmation --> Idle: 用户取消
    Executing --> Completed: 本地提交成功
    Executing --> Failed: 校验或保存失败
    Failed --> AwaitingConfirmation: 修正或重试
    Completed --> Idle
~~~

只读查询可以直接执行；新建、修改、删除和计划替换先形成可编辑方案，再由用户确认。一次方案可包含多个相关变更，避免逐字段重复确认。

每次用户输入最多执行 8 次模型/工具步骤；连续两次相同且无新增结果的查询终止并提示补充信息。模型请求初始超时设为 30 秒，可按实测调整；不在无反馈状态无限重试。

## 5. 日期、任务与排程规则

### 5.1 日期规则

- 相对日期优先以通知发布时间为锚点；导入时间与发布时间分别保存。
- “明天”“下周五”遇到发布时间未知时追问，不直接按今天推断。
- “周五交”没有具体时刻时，保存为“当天到期”，不擅自补成 23:59。
- 日期精度区分 unknown、date_only、exact；无确切时间时不生成具体时刻的到期提醒。
- exact 使用带时区的时间；首版默认 Asia/Shanghai，date_only 另存本地日期。
- 截止时间已过去时提示确认；允许记录历史任务，不悄悄改成未来日期。
- 例行重复任务和复杂节假日推算不纳入首版。

### 5.2 任务状态

任务状态：todo、in_progress、ready、submitted、done、cancelled。

- 有提交要求的任务可从 ready 进入 submitted；提交状态由用户明确确认。
- 普通待办完成后进入 done；cancelled 表示不再执行。
- overdue 根据当前时间和截止字段派生，不作为独立持久化状态。
- 清单勾选表示用户已准备该材料，不表示应用验证了文件内容。

### 5.3 基础排程算法

输入：未完成任务、用户确认的剩余工时、未来七天可用时间块、既有安排、用户锁定的安排。

1. 根据任务截止日期和用户确认的优先级排序。
2. 以约 30 分钟为基础工作块，按剩余工时拆分。
3. 依次填入截止前的空闲时间；可用区间不包含课程、活动等不可用时间。
4. 保留已完成和锁定的时间块，避免重复安排同一工作量。
5. 校验时间块不重叠、工时不超过空闲容量、任务总安排与剩余工作一致。
6. 无法安排的部分明确返回 taskId、缺口工时与原因。

日期只有“当天到期”时，安排在该日期内并标记“具体截止时间待确认”；如用户要求严格保证截止前完成，先补齐确切时刻。

模型可解释安排和提出调整，但排程结果必须经过代码校验。排不下时让用户增加可用时间、调整工作量或联系发布者，不修改正式截止时间来制造可行结果。工时估计是用户可修正的计划输入，不代表保证完成。

## 6. Agent 工具与确认协议

### 6.1 工具定义

| 工具 | 输入 | 输出/作用 | 是否写入 |
|---|---|---|---|
| get_tasks | 课程、关键词、状态、日期范围 | 返回真实任务摘要和 ID | 否 |
| get_task_detail | taskId | 原 DDL、清单、来源、进度、版本 | 否 |
| get_notice | noticeId | 返回原通知与发布时间 | 否 |
| get_availability | 起止日期 | 可用时间和已占用区间 | 否 |
| propose_task_changes | 创建/修改/删除草案、来源 ID | 字段校验、前后差异、待确认方案 | 保存草案，不改变正式任务 |
| build_plan | taskIds、日期范围、偏好 | 计算候选时间块与未能安排的任务 | 否 |
| propose_plan_changes | 新时间块、替换范围 | 生成计划变更卡 | 保存草案，不改变正式计划 |
| apply_confirmed_proposal | proposalId、operationId、版本 | 校验确认记录并提交，返回实际结果 | 是，由客户端确认事件触发 |

模型仅能使用白名单工具，不能执行任意代码、SQL 或文件路径。apply_confirmed_proposal 由客户端控制，模型不能伪造用户确认。

### 6.2 工具返回约定

所有工具返回 success、data、errorCode、message，写入工具额外返回 operationId 和 committedRevision。

错误码至少包含：NOT_FOUND、AMBIGUOUS_TARGET、INVALID_ARGUMENT、VERSION_CONFLICT、STORAGE_FAILED、CAPACITY_EXCEEDED。

- VERSION_CONFLICT：方案生成后数据发生变化，重新读取并展示方案。
- STORAGE_FAILED：正式状态未提交，保留可重试草案，不能回复“已保存”。
- CAPACITY_EXCEEDED：返回缺口，允许保存可行部分前须清楚标出未安排项。
- 工具失败时模型获得失败结果，回复明确的可恢复操作。

### 6.3 幂等与一致性

每次确认生成唯一 operationId；同一 operationId 重试时返回已提交结果，防止重复创建任务。

方案记录 expectedRevision，提交前比较任务库版本。正式任务、通知关联、计划变化和操作结果在同一个本地事务/快照中提交。确认后界面先读取提交结果，再更新任务卡。

用户快速点击、网络回复丢失或应用中途退出，不应造成同一任务重复写入。恢复待确认草案时不得自动执行，需要重新校验版本并由用户确认。

~~~

Agent 编排、工具实现和任务业务规则放在共享客户端，服务端承担云端调用和密钥管理。任务与会话的权威数据在本机；客户端只向模型发送完成当前请求所需的上下文。

ArkUI-X 官方工程说明采用共享 ArkTS 主代码与各端平台工程组合的结构，具体工具链、支持接口和桥接方式需以选定版本验证结果为准。[官方工程结构说明](https://github.com/arkui-x/docs/blob/master/zh-cn/application-dev/quick-start/package-structure-guide.md)

### 7.2 建议选型

| 层次 | 建议 | 选择理由与约束 |
|---|---|---|
| 客户端 | ArkUI-X + ArkTS | 满足一套 UI 和核心业务代码跨端要求 |
| Agent | 共享 ArkTS 中的轻量状态机和工具分发 | 流程有限，便于调试、展示与控制范围 |
| 模型网关 | Python FastAPI | 仅承担模型、语音请求和结构校验，减少后端业务 |
| 模型 | 一种支持结构化响应/工具调用的云端模型 | 了解一个候选服务，通过真实调用确认可用性、中文效果、成本和延迟 |
| 本地存储 | 首版采用文件 JSON 快照，通过 LocalStore 封装 | 数据规模小；原子替换/恢复语义须在两端验证 |
| 语音 | SpeechAdapter，鸿蒙必做 | 优先验证实际设备可用能力；必要时使用录音+云端 ASR/TTS |
| 排程 | 本地确定性规则 | 可校验、可解释，不依赖模型生成时间表的正确性 |
| 系统提醒 | ReminderAdapter，P1 | 依赖实际平台能力；应用内到期列表始终可用 |

选型是建议，不代表已完成依赖安装或设备兼容性验证。先检查已有环境、准备开发工具并列出设备与工具缺项，再通过模板构建验证 DevEco Studio、ArkUI-X SDK、鸿蒙设备系统/SDK、Android SDK/JDK/Gradle 的兼容组合，记录实际版本。工程搭建与各模块的资料准备可按依赖并行开展。

### 7.3 平台适配边界

| 共用内容 | 允许的平台差异 |
|---|---|
| 页面、任务卡、变更卡、对话展示、状态管理 | 包配置、签名、权限、应用入口 |
| Agent 状态机、工具协议、模型调用协议 | 文件、录音、音频播放和系统提醒的必要桥接 |
| 日期解析后的校验、任务规则、排程、数据结构 | 平台生命周期回调与能力是否可用 |

鸿蒙原生 Kit 不默认视为 Android 可用接口。Android 未实现语音时，SpeechAdapter 返回能力不可用，保留完整文本主流程。不能用 Android 原生页面重新实现核心业务。

## 8. 数据模型与本地存储

### 8.1 主要实体

| 实体 | 主要字段 |
|---|---|
| Notice | id、rawText、sourceLabel、publishedAt、importedAt、timezone、contentHash |
| Task | id、title、course、kind、deadlinePrecision、deadlineDate、dueAt、timezone、priority、status、remainingMinutes、submissionChannel、noticeIds、version、createdAt、updatedAt |
| ChecklistItem | id、taskId、label、state、sourceNoticeId、confirmedAt |
| AvailabilityBlock | id、startAt、endAt、label |
| PlanBlock | id、taskId、startAt、endAt、state、locked、planRevision |
| Proposal | id、sessionId、kind、changes、sourceNoticeIds、expectedRevision、state、createdAt |
| Operation | operationId、proposalId、resultStatus、affectedTaskIds、committedRevision、createdAt |
| Session | id、title、createdAt、updatedAt、pendingProposalId |
| Message | id、sessionId、role、text、toolName、toolResultSummary、status、createdAt |

deadlinePrecision 为 exact 时使用 dueAt；date_only 时使用 deadlineDate；unknown 时两者为空。ChecklistItem.state 首版采用 pending/prepared。用户确认提交的信息记录到任务状态和操作记录。

### 8.2 持久化方案

- task-store.json：通知、任务、清单、时间块、方案、操作记录和全局 revision，作为一份业务快照。
- sessions/：每个会话独立存储消息与会话元数据。
- settings.json：时区、显示偏好等；不存服务商密钥。

业务写入采用串行写队列：构造新快照 → 校验 → 写临时文件 → 原子替换主文件。保留上一份有效快照用于恢复；具体文件替换语义通过平台适配层验证。

在业务功能依赖本地写入前，验证文件快照方案的两端行为；若选定工具链无法可靠实现，切换到经过两端验证的事务存储适配，再继续集成业务写入。上层业务不依赖具体存储 API。

### 8.3 数据规则

1. 重启后加载完整任务、计划和会话；会话保存失败需提示，不能仅存在内存中。
2. 离线可查看、人工编辑和删除本地数据；AI 新请求提示需要网络。
3. 会话删除移除该会话消息及相关未提交草案；已确认创建的任务仍存在，界面说明这一行为。
4. 删除任务时一并移除其计划块与清单；剩余来源记录按关联情况清理。
5. 去重综合原文、发布时间、课程和候选任务，不能只按标题相同判定。
6. schemaVersion 用于存储结构升级；读取失败时保留损坏文件，提示恢复，避免直接覆盖。

## 9. 服务端接口与模型交互

### 9.1 首版接口

| 接口 | 作用 |
|---|---|
| POST /api/model/turn | 接收当前消息、必要上下文、白名单工具定义及已执行工具结果，返回文本或规范化工具调用 |
| POST /api/speech/asr | 仅云端语音方案使用：音频转写 |
| POST /api/speech/tts | 仅云端语音方案使用：短文本转音频 |
| GET /health | 联调和演示前检查服务状态 |

model/turn 返回类型包括 answer、tool_calls、clarification。服务端保留 requestId 便于关联错误，不把模型自然语言中的“成功”当写入证据。缺少原生工具调用能力的模型，可使用结构化动作协议，但必须校验动作名与参数。

服务端不承担首版任务同步，也不保存完整会话库。调用日志仅记录请求编号、耗时、错误和用量统计，避免写入完整通知、音频与密钥。

### 9.2 模型行为约束

- 查询、修改前使用真实工具结果，不虚构任务 ID 或已有任务内容。
- 通知原文作为待提取数据；其中的文字不能改变系统规则或扩大工具权限。
- 不自行编造日期、材料要求、工时或提交状态；推测必须作为待确认项。
- 多个候选任务时追问，不静默覆盖。
- 返回格式不合法时最多进行一次结构修复；仍失败则提供人工录入入口。
- 正式写入成功后按实际结果反馈；失败时给出修正或重试方式。

服务商密钥放在服务端环境变量，使用占位配置示例；不写入仓库或安装包。演示服务需访问凭证和基本频率限制，客户端凭证仅允许访问本项目网关，不具有服务商权限。

## 10. 鸿蒙语音交互设计

### 10.1 链路

点击录音 → 请求麦克风权限 → 录制 → ASR 转写 → 展示可编辑文字 → 提交给共用 Agent → 显示结果/确认卡 → TTS 播报简短摘要。

语音描述可以创建待确认方案；正式写入仍通过屏幕确认。首版不必支持复杂的语音连续确认。

### 10.2 接口与状态

SpeechAdapter 统一提供 capability、startRecording、stopRecording、recognize、speak、stopSpeaking、cancel。

状态至少包含 idle、recording、recognizing、ready、speaking、error。点击“停止播报”应立即停止；离开录音页取消录音，应用转后台时清楚处理录音与播放状态。

### 10.3 实现选择与风险收敛

在语音业务集成前，验证鸿蒙设备上可用的 ASR/TTS 路径。若原生能力受 SDK、系统或设备限制，使用统一录音接口接云端 ASR/TTS，业务链路保持不变。

录音格式、时长和上传方式按服务商要求确定，首版建议单次最多约 30 秒。识别为空或误识别时允许重录和编辑；不能将模型调用失败或 ASR 失败伪装为完整语音成功。文本回退可用于恢复操作，但不能替代鸿蒙语音验收。

## 11. UI 与交互

### 11.1 信息架构

| 页面 | 主要内容 | 关键操作 |
|---|---|---|
| 今日 | 今天安排、临近 DDL、未安排项 | 标记进度、查看安排、粘贴通知 |
| 任务 | 按课程、状态、日期筛选的任务列表 | 编辑任务、查看清单和来源、删除 |
| 助手 | 文本/语音输入、对话、任务卡、变更卡 | 补充信息、确认或修改方案 |
| 我的 | 本地会话历史、偏好和基本说明 | 回看与删除会话、设置时区 |

任务详情展示正式 DDL、工作安排、材料清单、原通知和变更记录；DDL 与“计划什么时候做”使用不同标签。

### 11.2 交互原则

- 首页主入口为“添加通知”和“查看今天安排”，减少进入聊天后才能找到任务的步骤。
- 创建卡展示关键字段；变更卡展示旧值、新值和来源；计划卡展示调整范围。
- 无具体截止时刻时明确显示“当天到期”；不使用看起来精确的虚构时间。
- 处理状态区分“理解通知”“查询任务”“等待确认”“正在保存”，完成后展示真实结果。
- 空态提供简短示例；错误态提供重试、编辑或取消按钮。
- 到期风险同时用文字和图标表达，不只依赖颜色。
- 鸿蒙和 Android 共用颜色、字号、间距、图标与组件样式；适配不同屏幕。
- P1 采用轻量列表入场、按压反馈、卡片展开和录音动效。

## 12. 失败与边界处理

| 情况 | 预期行为 |
|---|---|
| 没有截止日期 | 追问；允许保存待补充任务，不擅自设日期 |
| 只有“周五”且通知发布时间未知 | 补充发布时间或直接选择日期 |
| 同名报告多于一个 | 展示候选与课程，让用户选择 |
| 原通知与补充通知冲突 | 展示两份来源及差异，由用户确认采用哪项 |
| 相同通知再次导入 | 提示候选重复，允许关联已有任务或明确创建新任务 |
| 网络断开、服务超时 | 保留输入和草案；本地历史仍可查看 |
| 模型参数或格式不合法 | 校验失败、有限修复，提供人工录入 |
| 工具执行失败 | 不更新界面为成功；保留修正或重试入口 |
| 连续点击确认 | operationId 去重，一次写入 |
| 草案期间用户手工修改任务 | 版本冲突，重新生成差异并确认 |
| 剩余任务超过空闲容量 | 展示缺口与未安排项，不强行塞入或改变 DDL |
| 麦克风/通知权限拒绝 | 说明恢复方式；文本或应用内列表可继续用 |
| ASR 错误、TTS 失败 | 可编辑转写、重录或重播；对话结果与音频状态分开 |
| 应用中途退出 | 已提交数据保留；待确认方案恢复后重新校验 |
| 用户说“做完了”但提交情况未知 | 分别记录准备完成和是否已提交，按任务类型追问 |

### 14.2 依赖与协作规则

- 环境、模型资料、数据字段和页面草图可以并行准备；开始具体集成前，先确认所依赖的接口与平台能力可用。
- 工程与网关、数据与语音等模块可分头实现，依赖尚未完成时可使用明确标注的模拟数据推进独立开发；真实调用和正式验收必须使用实际能力。
- 正式保存与更新依赖持久化、确认、幂等和版本机制；排程与重排依赖真实任务、可用时间和规则校验。
- 页面、语音、模型和数据对接时，以共同确认的参数、返回值、错误码和示例为准；接口变更同时更新说明并由相关成员评审。
- 每项任务完成后记录实际验证、关联 PR 和尚存问题。可以继续拆分子任务，但须保留原任务的完成标准和责任归属。
- 联调使用同一主分支提交，鸿蒙与 Android 采用一致示例分别验证；两端状态一致指同一逻辑与相同输入下行为一致，不新增跨设备自动同步承诺。

### 14.3 按完成条件验收

| 检查点 | 应具备的结果 | 验证重点 |
|---|---|---|
| 基础能力 | 两端模板、真实文本模型调用、本地历史、鸿蒙最小语音链路；通知草案与缺项追问可用 | 工具链与能力确实可运行，两端重启可回看，语音全链路有证据 |
| 核心业务 | 通知转任务、补充通知更新、进度变化后重排三个闭环均可演示 | 确认后真实写入，取消不写，重试不重复；歧义可追问，正式 DDL 不被排程改写 |
| 交付候选 | 兼容回归、样例检查和试用问题收敛，两端候选版本与交付文档齐备 | 功能冻结，构建记录、配置示例、数据、架构和演示材料与同一版本对应 |
| 最终交付 | 干净环境复现通过，模型与异常演示可用，重启/删除/数据复验完成，材料与验收清单完整 | 两端产物或运行说明可复现，演示可信，未完成范围与限制明确 |

检查点依据实际完成情况推进，不设日历日期或完成期限。准备资料本身可以独立验收；资料完成不代表工程、模型、存储或语音已经实现。

### 14.4 范围调整原则

- 语音、存储或两端构建阻塞时集中处理；基线未通过则暂停 P1/P2，优先补齐必做能力。
- 核心业务未闭环时，优先简化计划视图、动效和提醒，不删除命题基线。
- 进入兼容回归与交付准备后，原则上不引入新平台、大型依赖或全新业务；必要调整须说明影响并安排相应复验。
- 形成交付候选版本后冻结功能，集中完成必要修复、打包、数据核验与演示复现。

## 15. 验证与验收

### 15.1 业务样例集

准备至少 30 条脱敏或人工构造通知，人工标注课程、日期精度、提交物、渠道、预期追问、创建/更新目标。覆盖明确日期、相对日期、无日期、补充通知、同名任务、重复通知和无任务内容等情况。

建议目标：明确且完整通知的关键字段整体正确率达到 90% 以上；歧义与缺项样例应追问或标记未知，不以“猜到日期”计作正确。记录样例总数、分组数量、错误类型，目标是内部改进标准，不是已经取得的成绩。

### 15.2 必需检查

| 类别 | 检查 | 通过条件 |
|---|---|---|
| 跨端 | 同一提交构建并安装鸿蒙、Android | 两端进入主流程；共享源码可查 |
| 云模型 | 两端真实输入不同请求 | 收到云端返回，不使用固定假回复代替 |
| 鸿蒙语音 | 录音、转写、模型处理、播报 | 全链路成功，并可停止播报 |
| 本地历史 | 两端关闭应用、重启、离线回看 | 会话仍在；删除后重启不重新出现 |
| Agent 创建 | 导入通知并补齐缺项 | 确认后任务存在，来源可查看 |
| Agent 更新 | 导入延期通知 | 原任务变更，不无故生成第二条 |
| 幂等/版本 | 重复确认、草案后人工修改 | 一次写入；版本冲突要求重新确认 |
| 排程 | 多任务、固定空闲时间、容量不足 | 无重叠；正式 DDL 不变；未安排项明确 |
| 提交状态 | 报告完成但附件缺失 | 清单仍显示缺项，提交状态需用户确认 |
| 异常 | 断网、超时、权限拒绝、保存失败 | 无假成功；输入保留；可恢复 |

自动化检查优先用于日期规则、排程不变量、任务状态转换、幂等和版本冲突；页面视觉、语音和两端安装通过实际操作验证。按风险编写有效检查，不为每个简单页面增加重复测试。

### 15.3 演示脚本

固定示例数据和时区，使用明确日期，避免现场对“下周五”的解释不一致。

1. 展示鸿蒙和 Android 由同一代码库构建的主界面。
2. 粘贴通知：“数据库实验报告 10 月 16 日 23:59 前交，PDF 和源代码上传学习通。”
3. 展示提取卡、确认保存、任务详情及原通知。
4. 导入补充通知：“数据库报告延期至 10 月 18 日 23:59，新增运行截图。”
5. 展示原任务查询和前后差异，确认后查看更新结果。
6. 增加一项英语作业，设置两段可用时间。
7. 鸿蒙语音输入：“今晚有事，数据库报告还剩两小时，帮我重新安排。”
8. 展示容量检查和新安排；确认后由 TTS 播报结果。
9. 演示材料准备与“已提交”的区分。
10. 关闭并重启应用，回看会话；Android 展示文本、任务更新和本地回看。
11. 展示一次歧义追问或网络失败恢复。

现场保持真实模型服务可用；准备已录制的完整演示视频作为故障备份，并明确它是录制材料。缓存结果或固定数据只能用于介绍与测试，不能代替真实调用验收。
